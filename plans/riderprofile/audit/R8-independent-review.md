## Findings / follow-up risks

- **Medium: source navigation loses bike scope.** `convex/advice/groupAdvice.ts:97` onwards emits generic saddle/gearing/pressure/tool URLs for bike-specific rows; `src/components/profile/AdviceGroupsView.tsx:31` additionally removes every query/hash. Opening advice for bike B therefore does not convey B in the destination URL. This is not a measurement leak, but the destination may select a different default bike rather than the reviewed source. Parent/A should confirm the destination's supported scope contract before adding only an owned bike/session identifier. Current fit report links do retain the session in the pathname. Do not pass measurement values to solve this.
- **Low: displayed calendar date depends on runtime timezone.** `src/components/profile/AdviceGroupsView.tsx:64` formats dates in NL/EN but omits `timeZone`. An epoch close to midnight can show a different day between server and browser timezones. Decide whether timestamps intentionally use the rider's local day or a stable product timezone; if stable, use an explicit timezone. This is a boundary risk, not evidence that ordinary displayed dates are incorrect. Saved-input dates are correctly labeled as saved dates, not calculation dates.
- **Known async limitation, not a false-fresh bug:** `AdvicePageClient.tsx:48` retains the mutation result as a historical summary; pending records are not joined to rows by recordId and there is no reactive background job status. A subsequently completed/failed fit does not change that summary's “started” count. The current wording says started rather than completed and the rows stay query-driven, so it does not falsely assert success. If per-row progress/error is required, parent needs a persisted job contract rather than interpreting replacementId as an advice row ID. Retry/reload also cannot reconstruct that progress from groups alone.
