## Findings

### P1 — Checkout cannot accept the actual login code

`src/components/checkout/CheckoutFlow.tsx:161` uses numeric input, `[0-9]{6}`, maxLength 6 and removes all letters. `src/i18n/marketing/checkout.ts:12` and `:26` also promise a six-digit code. Actual auth contract at `convex/auth.ts:20` / `:21` / `:80` generates SEVEN characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`. A delivered code such as ABC2345 becomes 2345 in this input and cannot pass form validation; even an all-digit generated code is seven characters and gets truncated. Every unauthenticated checkout requiring manual verification is blocked. The current auth test supplies a mocked six-digit 123456 and therefore misses this integration mismatch. Align the input/copy with the actual auth code contract and test a seven-character alphanumeric code; no backend code-format change is needed.

### P2 — Reload from a pricing URL loses the latest persisted selection

`src/app/(checkout)/checkout/page.tsx:9` provides initialSelection whenever product or bikeId appears in the URL. `src/components/checkout/CheckoutFlow.tsx:49` always prefers that initialSelection over readCheckoutSelection. Choosing a product/bike persists storage but does not update URL (`:68`). Repro: enter /nl/checkout?product=single, select owned bike A and reach confirm, then reload that same URL. The selected bike is reset to empty despite having been saved. Similarly, enter with annual, switch to personal, reload: annual silently wins. Current remount test has no initialSelection and does not cover the actual pricing-entry URL. Define URL versus saved-draft precedence, update the URL as selection changes or merge a compatible saved bike, then test actual entry URLs. A new explicit product link must still override an unrelated old draft.

### P2 — Reactive price/selection changes do not invalidate consent

`CheckoutFlow.tsx:35` stores consent independently. User-triggered choose/advance/back/retry correctly clear it (`:68`, `:75`, `:123`, `:135`), but changing `introEligible` changes canonical product/price (`:41`) without clearing consent or the previous stub status. Likewise the initialSelection effect (`:49`) can replace the selected product/bike without resetting consent. Repro in a component rerender: confirm eligible annual_entry at €13.50, check consent, then rerender introEligible=false; price becomes €24.50 with consent still checked and Pay enabled. This can follow a reactive entitlement/refund update. Invalidate consent/status when effective product ID, price, selected bike or account identity changes. No money/access can currently be affected because Pay only calls the pure stub; this is a confirmation-state defect.

### Scope clarification — entry gift feature exceeds the literal exception

`src/i18n/marketing/checkout.ts:10` / `:24` advertise one measurement to give away for annual_entry. The mobile Kies board shows that feature, but pricing-v3 README's explicit release-2.0 exception names only “2 losse metingen om weg te geven”; its general rule excludes gifts. Worker contract consciously retains annual 2 / intro 1. Parent should resolve that narrow scope conflict (remove entry gift line or explicitly authorize it); this is not an entitlement/security finding.

No fetch, purchase mutation, entitlement grant, mail or success transition in that path. Checkout does not call transition redemption. Bike ID here is a saved draft, not a newly granted entitlement.
- Entry: `CheckoutClient.tsx:13` reads authenticated getSubscription; query filters by auth user (`convex/pricing/queries.ts:14`). Subscription loading blocks progress/pay. URL/storage annual_entry normalizes to annual, then checkoutProductId upgrades only from authenticated server eligibility. - Single: bike comes from authenticated listByUser (`convex/bikes/queries.ts:423`), matched against selected ID before Pay. Missing, loading or foreign IDs cannot invoke stub. Changing bike through the selector clears consent. A future real checkout endpoint must independently revalidate ownership/eligibility; absence of that endpoint is intentional in this stub-only release.
- Storage: actual implementation uses localStorage, NOT sessionStorage (`checkout-state.ts:35`, `:44`). No sessionStorage recovery exists. Reads whitelist product IDs and require string bikeId; malformed/unavailable storage is caught. Only product/bike are returned; consent/email are not restored. Storage failure blocks proceeding/stub rather than falsely claiming a save. Shared-origin localStorage is not scoped to account/tab and persists after tab close; another tab/account may inherit an irrelevant draft, but current ownership/eligibility checks prevent granting access. If session-scoped recovery was intended, choose sessionStorage explicitly. Existing contract only promises persistence, so this is recorded separately from the concrete reload bug.
- Login locale: route getRequestLocale and withLocalePrefix preserve NL/EN in redirectTo; CheckoutClient passes locale too. Actual email locale is derived from the redirect URL (convex/auth.ts:144 → convex/emails/locale.ts), not trusted from the extra locale field. Installed auth signIn implementation passes the localized redirect URL to sendVerificationRequest, so no locale mismatch found. No real login email sent during review.
