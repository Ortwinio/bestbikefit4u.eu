# Migration Gaps: Prototyper UI

## Status

The current state is a partial migration to `@base-ui/react`, not a completed migration to "only Prototyper UI components."

## What Is Still Missing

- The repo does not contain Prototyper UI component source files generated by the Prototyper CLI.
- The current primitives in `src/components/ui/` are still local custom implementations.
- `Button` and `Card` are still entirely custom components.
- `Input`, `Select`, `Tooltip`, `AccessibleDialog`, and `Progress` are compatibility wrappers over Base UI primitives, not copied Prototyper UI components.
- `States.tsx` and `src/components/questionnaire/ProgressBar.tsx` are still custom composed components.

- `src/components/ui/Button.tsx`

- hand-written Tailwind classes inside the local primitives

## What Has To Be Done

### 1. Install Actual Prototyper UI Source

Run the Prototyper CLI and add the actual source for:

- `button`
- `input`
- `label`
- `select`
- `card`
- `dialog`
- `tooltip`
- `progress`

### 2. Replace Local Custom Primitive Implementations

Replace the current local implementations in `src/components/ui/` with the copied Prototyper source files.

### 3. Choose a Migration Mode

There are two valid paths:

- Compatibility mode: keep the current exports like `Button`, `Input`, `Select`, and `AccessibleDialog` as thin adapters over copied Prototyper UI components.
- Pure Prototyper mode: refactor consumers to use the Prototyper APIs directly.

### 4. Refactor the High-Churn APIs

If the goal is pure Prototyper mode, the main refactors are:

- `Input`: current consumers rely on `label`, `tooltip`, `error`, and `helperText` on one component.
- `Select`: current consumers rely on `options[]`, `placeholder`, and native-like `onChange`.
- `AccessibleDialog`: current consumers rely on `open`, `title`, `description`, `onClose`, and `children`.

### 5. Remove Temporary Custom Styling Glue

Once Prototyper source is in place, remove the styling glue that exists only to simulate a component library:

- `class-variance-authority` usage in `Button.tsx`
- `class-variance-authority` usage in `Card.tsx`
- wrapper-only custom class logic that duplicates Prototyper source behavior

### 6. Re-run Validation

After the real Prototyper migration lands:

- run `npm run typecheck`
- run `npm run build`
- run targeted UI tests
- run the migration test plan in `plans/feature-prototyper-ui-migration/TESTPLAN.md`
- complete manual browser checks for forms, dialogs, questionnaire flow, and results flow

## Remaining Blockers Outside The UI Migration

Even if the Prototyper migration is finished, the broader plan still is not complete until repo-level validation issues are resolved:

- `npm run lint` currently fails for unrelated existing issues outside this migration
- `npm test` currently fails for unrelated existing Convex tests
- manual browser validation steps are still outstanding

## Bottom Line

The current implementation is a compatibility-first Base UI migration, not a strict Prototyper UI migration.

To complete the migration and use only Prototyper UI components, the repo still needs:

1. actual Prototyper source files
2. replacement of the local custom primitive implementations
3. consumer refactors or compatibility adapters over the copied Prototyper components
4. full validation against the migration test plan
