## Changes

- Verified payment transactions persist a unique mail job and schedule an action, never call a provider in the webhook transaction. One-off purchase keys use payment intent; first-invoice welcome and cancellation keys use subscription plus period start. Renewal and expiry keys use period/entitlement. The latest cancelled period is selected, including cancellation-before-invoice delivery order.
- All five billing triggers are wired. Daily scans are paginated (50 records) with bounded continuations. The renewal lead time is a constant, default 30 days pending the owner decision. Paid renewal periods are not confused with superseded periods; cancelled subscriptions skip renewal reminders but can receive expiry notices. Current replacement access suppresses expiry.
- Persisted atomic claims, stable provider keys, frozen request bodies and bounded retries prevent duplicate dispatch in tested replays, concurrent claims and crash/retry cases. A frozen request is kept in the database only and cleared after confirmed success; no recipient, body or webhook payload is written to audit logs. Changed recipients fail closed. Six delivery attempts within 20 hours stay inside provider idempotency retention; terminal/ambiguous failures require reconciliation, not blind replay.
- Missing payment/refund evidence remains pending without consuming provider attempts. Signed invoice/payment/refund events wake those jobs, including late repeated invoices attaching identity. Full refunds cancel pending purchase/welcome/renewal/expiry delivery. Cancellation confirmations instead require the exact tagged successful cancellation refund, not any unrelated partial refund or cumulative refunded amount. Rounded zero-cent pro-rata refunds need no nonexistent refund event.
- `refund.created` and `refund.updated` supplement the original twelve shared webhook events. Installed Stripe declarations mark charge refund expansion optional and explicitly direct consumers to refund events for refund details. C owns the shared list/catalogue configuration; events.ts imports it. Successful tagged refund evidence is stored additively and cannot silently change its key or amount.
- Service preference and current NL/EN locale are read at delivery; marketing consent is not required. Both appointment products use validated HTTPS agenda links. Unknown purchase products and missing booking configuration fail closed. Seven sender kinds have bilingual tests.
- Transition announcement/reminder batches require a billing administrator, matching completed dry-run evidence, bounded pages (25), one-use apply evidence and a 24-hour run/evidence window. Only aggregate counts and an opaque run handle are returned. Targets have at least one report; reminders require an unredeemed offer expiring within seven days. Queue keys deduplicate per campaign/user or offer/user.
- The prelaunch announcement alone can run with billing flags OFF, because a fourteen-day announcement precedes launch. This is not a Stripe payment API exception: persisted reciprocal admin/dry-run proof is verified at queue and claim. Other billing mails and reminder batches remain flag-gated. No announcement was actually sent.
